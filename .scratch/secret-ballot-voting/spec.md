# 스펙: 명부 기반 비밀 투표 (v1)

Status: ready-for-agent

## Problem Statement

동아리·학생회 같은 소규모 조직은 회식 메뉴 같은 가벼운 결정부터 임원 선거 같은 실제 선거까지 구성원의 뜻을 물어야 할 일이 많다. 지금은 카톡 투표나 손을 드는 방식에 의존하는데, 이 방식에는 세 가지 문제가 있다.

- 누가 투표할 자격이 있는지 확인할 수 없다.
- 한 사람이 여러 번 투표하는 것을 막을 수 없다.
- 누가 무엇을 골랐는지 드러나서 비밀 투표가 되지 않는다.

운영자 입장에서는 투표를 올리고 정리하는 도구가 없고, 투표자 입장에서는 휴대폰으로 간단히 투표하고 결과를 확인할 방법이 없다.

## Solution

휴대폰에서 쓰는 한국어 웹앱을 만든다.

- **운영자**는 공용 운영자 비밀번호로 로그인해 투표자 명부를 관리하고, 투표자마다 개인 투표 코드를 발급하며, 투표를 만들고 삭제한다.
- **투표자**는 운영자에게 받은 투표 코드를 기기에서 한 번 입력한다. 그 뒤로는 투표 목록에서 투표를 골라 선택지 하나에 투표하고, 투표한 뒤에는 결과를 본다.
- **비밀 투표**: 앱은 누가 참여했는지(참여 기록)만 알고 누가 무엇을 골랐는지는 저장하지 않는다. 운영자도 알 수 없다.
- 한 번 한 투표 행위는 바꾸거나 취소할 수 없다.

## User Stories

### 투표자: 입장

1. 투표자로서, 운영자에게 받은 투표 코드를 입력해 입장하고 싶다. 그래야 명부에 있는 본인으로 인정받는다.
2. 투표자로서, 코드를 대소문자나 공백·하이픈 구분 없이 입력하고 싶다. 그래야 받은 대로 대충 입력해도 통과된다.
3. 투표자로서, 헷갈리는 글자(0/O, 1/I/L)가 없는 코드를 받고 싶다. 그래야 잘못 입력할 일이 적다.
4. 투표자로서, 같은 기기에서는 코드를 한 번만 입력하고 싶다. 그래야 투표할 때마다 코드를 찾지 않아도 된다.
5. 투표자로서, 코드가 틀리면 분명한 안내를 받고 싶다. 그래야 운영자에게 코드를 다시 확인할 수 있다.
6. 투표자로서, 공용 기기에서는 "코드 지우기"로 기억된 코드를 지우고 싶다. 그래야 다른 사람이 내 이름으로 투표하지 못한다.
7. 투표자로서, 재발급되었거나 명부에서 빠진 코드로는 더 이상 들어갈 수 없기를 바란다. 그래야 유출된 코드가 계속 쓰이지 않는다.
8. 투표자로서, 투표 링크를 코드 없이 열었을 때 코드 입력 화면이 먼저 나오고, 입력하면 원래 보려던 투표가 보이길 바란다. 그래야 카톡 링크를 바로 눌러도 된다.
9. 투표자로서, 화면 위에서 내 이름을 확인하고 싶다. 그래야 내 코드로 들어왔는지 알 수 있다.

### 투표자: 목록과 투표

10. 투표자로서, 올라온 투표를 최신순으로 보고 싶다. 그래야 새 투표를 먼저 찾는다.
11. 투표자로서, 목록에서 이미 투표한 투표에 "투표 완료" 표시가 붙길 바란다. 그래야 남은 투표만 챙길 수 있다.
12. 투표자로서, 투표가 없을 때 "아직 올라온 투표가 없어요" 안내를 보고 싶다. 그래야 앱이 고장 난 건지 헷갈리지 않는다.
13. 투표자로서, 투표를 열면 제목과 선택지를 보고 하나를 고르고 싶다.
14. 투표자로서, 투표하기 전에는 결과를 볼 수 없기를 바란다. 그래야 기운 쪽을 따라가는 투표를 막을 수 있다. 화면뿐 아니라 브라우저로 전달되는 데이터에도 결과가 없어야 한다.
15. 투표자로서, 투표 직전에 "바꾸거나 취소할 수 없다"는 확인 창을 보고 싶다. 그래야 실수로 누르지 않는다.
16. 투표자로서, 선택지를 고르지 않고 제출하면 고르라는 안내를 받고 싶다.
17. 투표자로서, 투표하면 곧바로 결과 화면으로 바뀌길 바란다.
18. 투표자로서, 버튼을 여러 번 누르거나 여러 기기에서 동시에 투표해도 한 번만 반영되길 바란다. 그래야 1인 1표가 지켜진다.
19. 투표자로서, 이미 투표한 투표에 다시 투표하려 하면 "이미 참여했어요" 안내와 함께 결과를 보고 싶다.
20. 투표자로서, 투표하려던 투표가 그사이 삭제되었다면 "삭제된 투표예요" 안내와 목록으로 돌아가는 버튼을 보고 싶다.
21. 투표자로서, 내 선택이 누구에게도, 운영자에게도 드러나지 않기를 바란다. 그래야 부담 없이 소신껏 투표한다.

### 투표자: 결과

22. 투표자로서, 투표한 뒤 선택지별 표 수, 비율, 가로 막대를 보고 싶다.
23. 투표자로서, 총 참여 수를 보고 싶다.
24. 투표자로서, 가장 많이 득표한 선택지가 눈에 띄길 바란다.
25. 투표자로서, 투표한 기기에서는 내가 고른 선택지에 "내 선택" 표시가 붙길 바란다.
26. 투표자로서, 다른 기기에서 코드를 입력해도 결과를 볼 수 있길 바란다. 이때 "내 선택" 표시는 없어도 된다.
27. 투표자로서, 새로고침하면 최신 결과를 보고 싶다.
28. 투표자로서, 표가 하나도 없는 투표의 결과도 오류 없이 0표·0%로 보고 싶다.

### 운영자: 로그인

29. 운영자로서, 공용 운영자 비밀번호로 로그인하고 싶다. 그래야 여러 운영진이 같은 비밀번호로 운영할 수 있다.
30. 운영자로서, 로그인이 7일 동안 유지되길 바란다. 그래야 휴대폰에서 매번 비밀번호를 치지 않는다.
31. 운영자로서, 로그아웃 버튼으로 직접 로그인을 끝내고 싶다.
32. 운영자로서, 비밀번호를 바꾸면 기존 운영자 로그인이 모두 끊기길 바란다. 그래야 비밀번호가 샜을 때 대처할 수 있다.
33. 운영자로서, 로그인하지 않은 사람이 운영자 화면이나 운영자 기능에 접근하면 막히고 로그인 화면으로 보내지길 바란다. 화면을 거치지 않은 직접 요청도 막혀야 한다.
34. 운영자로서, 비밀번호가 틀리면 분명한 안내를 받고 싶다.
35. 운영자로서, 투표자 코드 입력 화면에서 운영자 로그인으로 갈 수 있길 바란다.

### 운영자: 투표자 명부

36. 운영자로서, 이름을 한 줄에 하나씩 붙여 넣어 여러 투표자를 한 번에 등록하고 싶다.
37. 운영자로서, 등록하면 투표자마다 투표 코드가 자동으로 발급되길 바란다.
38. 운영자로서, 이미 명부에 있는 이름이 섞여 있으면 아무것도 등록되지 않고 어떤 이름이 겹쳤는지 안내받고 싶다. 그래야 동명이인을 "김철수(21학번)"처럼 구분할 수 있다.
39. 운영자로서, 입력한 목록 안에 같은 이름이 두 번 있거나 이름이 20자를 넘으면 안내를 받고 싶다.
40. 운영자로서, 등록에 실패해도 입력한 이름이 지워지지 않길 바란다. 그래야 고쳐서 다시 제출할 수 있다.
41. 운영자로서, 명부를 이름순으로 보고, 각 투표자의 코드를 확인하고 싶다.
42. 운영자로서, "이름: 코드" 목록 전체를 한 번에 복사하고 싶다. 그래야 카톡 개인 메시지로 빠르게 나눠줄 수 있다.
43. 운영자로서, 코드를 잃어버린 투표자의 코드를 재발급하고 싶다. 재발급하면 이전 코드는 바로 무효가 되어야 한다.
44. 운영자로서, 투표자를 명부에서 빼고 싶다. 뺀 투표자의 코드는 바로 무효가 되고, 이미 한 투표는 결과에 그대로 남아야 한다.
45. 운영자로서, 명부에서 뺀 이름을 나중에 다시 등록할 수 있길 바란다.
46. 운영자로서, 재발급하거나 뺄 때 확인 창을 보고 싶다.
47. 운영자로서, 코드는 본인에게만 보내야 한다는 안내를 보고 싶다.

### 운영자: 투표 관리

48. 운영자로서, 제목(100자 이하)과 선택지(2~10개, 각 50자 이하)로 새 투표를 만들고 싶다.
49. 운영자로서, 투표를 만들 때 선택지 칸을 추가하거나 삭제하고 싶다. 최소 2칸, 최대 10칸까지다.
50. 운영자로서, 제목과 선택지의 앞뒤 공백이 자동으로 정리되고, 빈 선택지 칸은 무시되길 바란다.
51. 운영자로서, 같은 투표 안에 같은 문구의 선택지가 있으면 안내를 받고 싶다.
52. 운영자로서, 투표를 만드는 데 실패해도 입력한 제목과 선택지가 지워지지 않길 바란다.
53. 운영자로서, 투표를 만들면 바로 그 투표의 관리 화면으로 가고 싶다.
54. 운영자로서, 만든 투표는 수정할 수 없다는 안내를 보고 싶다. 그래야 틀렸을 때 삭제하고 다시 만든다.
55. 운영자로서, 여러 투표를 동시에 열어두고, 목록에서 투표별 참여 수를 보고 싶다.
56. 운영자로서, 투표하지 않고도 투표의 결과를 보고 싶다.
57. 운영자로서, 투표별로 참여한 투표자와 아직 참여하지 않은 투표자의 이름을 보고 싶다. 그래야 참여를 독려할 수 있다. 명단은 이름순이어서 참여 순서가 드러나지 않아야 한다.
58. 운영자로서, 누가 무엇을 골랐는지는 볼 수 없다는 안내를 보고 싶다.
59. 운영자로서, 확인 창을 거쳐 투표를 영구 삭제하고 싶다. 삭제하면 그 투표의 선택지, 결과, 참여 기록이 모두 사라진다.
60. 운영자로서, 운영자도 투표하려면 다른 투표자처럼 내 투표 코드를 쓰고 싶다. 운영자 로그인만으로는 투표가 기록되지 않아야 한다.

### 배포와 운영

61. 운영자로서, Vercel에 배포하고 Neon Postgres를 데이터베이스로 쓰고 싶다.
62. 운영자로서, 데이터베이스 연결 문자열과 운영자 비밀번호를 환경변수로만 설정하고 싶다.
63. 운영자로서, 테이블 생성 명령을 여러 번 실행해도 안전하길 바란다.

## Implementation Decisions

### 용어와 기존 결정

- 모든 이름은 CONTEXT.md의 용어를 따른다: 투표(Poll), 제목, 선택지(Option), 투표 행위(Vote), 참여 기록(Participation), 결과(Result), 투표자(Voter), 투표자 명부(Roster), 투표 코드(Voter Code), 운영자(Admin).
- 결정 기록 0001(명부와 개인 투표 코드, 투표 행위는 바꿀 수 없음)과 0002(참여 기록과 투표 행위 분리, 선택지별 개수만 저장)를 따른다.

### 모듈

- **투표 도메인 모듈** (이번 작업의 유일한 테스트 경계): 투표와 명부의 모든 규칙을 담는다.
  - 공개 인터페이스는 원시 입력을 받아 검증까지 스스로 한다. 호출하는 쪽은 검증을 따로 하지 않는다.
  - 지금은 입력 검증이 별도 규칙 모듈에 있고 Server Action에서 호출된다. 이 검증을 도메인 모듈 안으로 옮겨서 경계를 하나로 만든다.
  - 인터페이스 형태는 다음과 같다.
    - `createPoll(title, rawOptions)` → 성공 시 투표 ID, 실패 시 사용자에게 보여줄 오류 문구
    - `deletePoll(pollId)`
    - `getPoll(pollId)` → 제목과 선택지별 표 수, 없으면 null
    - `listPollsFor(voterId)` → 최신순, 투표 완료 여부 포함
    - `listPollsForAdmin()` → 최신순, 참여 수 포함
    - `castVote(pollId, optionId, voterId)` → `ok | already | gone`
    - `hasParticipated(pollId, voterId)`
    - `getTurnout(pollId)` → 참여 이름과 미참여 이름, 이름순
    - `addVoters(rawNamesText)` → 등록 수, 또는 검증 오류나 이미 있는 이름 목록
    - `removeVoter(voterId)`, `reissueCode(voterId)`
    - `listRoster()` → 이름순, 코드 포함
    - `findVoterByCode(rawCode)` → 코드 정규화까지 포함
  - 잘못된 형식의 ID는 오류를 던지지 않고 "없음"으로 처리한다.
- **세션 모듈**: 쿠키 기반으로 운영자와 투표자를 식별한다. 도메인 모듈에 의존하지만 도메인 모듈은 세션 모듈을 모른다.
  - 운영자 쿠키: 만료 시각과 HMAC 서명. 서명 키는 운영자 비밀번호이며, 7일 유지, httpOnly다.
  - 투표자 쿠키: 투표 코드 원문. 1년 유지, httpOnly다. 요청마다 명부에서 유효한지 다시 확인한다.
- **Server Action과 화면**: 얇은 계층이다. 권한을 확인하고, 도메인 모듈을 호출하고, 결과에 따라 화면을 바꾸는 일만 한다.
  - 운영자용 Server Action은 모두 처음에 운영자 권한을 확인한다.
  - 운영자 경로 전체는 Next 16의 `proxy`로도 일괄 가드한다(로그인 화면 제외). 이건 추가 방어일 뿐이고, 페이지와 Server Action 안의 권한 확인을 대신하지 않는다.

### 데이터

- **voters**: 이름, 코드(원문, 유일), 뺀 시각.
  - 명부에서 빼면 뺀 시각을 기록하고 코드를 비운다. 행은 남겨서 참여 기록을 보존한다.
  - 이름은 명부에 있는 투표자 사이에서만 유일하다(부분 유일 인덱스).
- **polls**: 제목, 생성 시각.
- **options**: 투표, 선택지 문구, 순서, 표 수.
  - 투표 안에서 순서와 문구가 각각 유일하다.
  - 투표를 삭제하면 함께 삭제된다.
- **participations**: (투표, 투표자) 복합 기본키. 시각은 저장하지 않는다. 투표를 삭제하면 함께 삭제된다.
- 투표 행위를 개별로 담는 테이블은 없다.
- 스키마는 `create ... if not exists`로만 구성하고, 여러 번 실행해도 되는 설정 명령으로 적용한다.

### 규칙

- **투표하기**: 참여 기록 추가(충돌하면 무시)와 해당 선택지의 표 수 증가를 **하나의 SQL 문**으로 처리한다.
  - 선택지가 그 투표에 속하지 않으면 둘 다 일어나지 않는다.
  - 실패하면 참여 기록 유무로 `already`와 `gone`을 구분한다.
- **투표 코드**: 헷갈리는 글자를 뺀 31자 알파벳(`ABCDEFGHJKMNPQRSTUVWXYZ23456789`)으로 된 무작위 8자리. 암호학적 난수로 만든다. 입력은 대문자로 바꾸고 공백과 하이픈을 제거해서 비교한다.
- **입력 제한**: 제목 100자, 선택지 2~10개(각 50자), 투표자 이름 20자. 앞뒤 공백을 제거하고, 빈 선택지는 무시한다. 같은 투표 안에서 선택지 문구가 중복되면 거부한다.
- **운영자 비밀번호 비교**: 두 값을 HMAC으로 만든 뒤 상수 시간으로 비교해서 길이와 시간 정보가 새지 않게 한다.

### 화면 동작

- 투표 전 화면에는 선택지의 ID와 문구만 전달한다. 표 수는 클라이언트로 보내지 않는다.
- "내 선택"은 투표에 성공했을 때 브라우저 로컬 저장소에만 기록한다. 서버로는 보내지 않는다.
- 투표 만들기와 명부 등록 폼은 오류가 나도 입력값이 남아야 한다. React 19의 form action 자동 초기화를 피해서 직접 제출한다.
- 파괴적인 동작(투표하기, 투표 삭제, 코드 재발급, 명부에서 빼기, 코드 지우기)은 모두 확인 창을 거친다.

## Testing Decisions

- **좋은 테스트의 기준**: 도메인 모듈의 공개 인터페이스만 호출하고, 사용자가 관찰할 수 있는 결과(돌려받은 값, 이후 조회 결과)만 확인한다.
  - 내부 SQL, 테이블 구조, 함수 내부 구현은 확인하지 않는다.
  - 예외가 하나 있다. 비밀 투표 보장은 "누가 무엇을 골랐는지 연결할 데이터가 없다"는 성질이라서, 스키마 수준에서 확인하는 테스트 한 개를 허용한다. 투표자와 선택지를 함께 참조하는 테이블이나 열이 없어야 한다.
- **테스트 경계는 하나**: 투표 도메인 모듈이다.
  - 세션 모듈, Server Action, 화면은 이번 범위에서 자동화 테스트를 하지 않는다. 얇은 계층이고 쿠키와 프레임워크에 묶여 있다.
- **도구와 환경**:
  - Vitest를 사용한다.
  - 실제 Postgres에 대고 실행한다. 테스트 전용 Neon 브랜치를 쓰고, `TEST_DATABASE_URL` 환경변수로 받는다.
  - 가짜 DB나 모킹은 쓰지 않는다. 동시성과 제약 조건이 핵심이라서 실제 Postgres에서만 의미가 있다.
  - 각 테스트는 고유 접두사로 데이터를 만들고 끝나면 지운다. 테스트끼리 서로 영향을 주지 않아야 한다.
  - 테스트 DB에는 테스트 시작 전에 스키마 설정 명령을 적용한다.
- **다룰 동작**:
  - 명부 등록: 한 번에 여러 명 등록, 코드 형식, 겹치는 이름이 섞이면 아무것도 등록하지 않음, 입력 안 중복과 길이 검증, 뺀 이름 재등록
  - 코드: 정규화된 입력으로 조회, 재발급 후 이전 코드 무효, 뺀 투표자의 코드 무효
  - 투표 만들기: 공백 정리, 빈 선택지 무시, 개수·길이·중복 검증, 선택지 순서 보존
  - 투표하기: 정상 투표, 두 번째 투표는 `already`, 동시 요청은 정확히 한 번만 `ok`, 다른 투표의 선택지는 `gone`이고 참여 기록도 남지 않음, 없는 투표나 잘못된 ID는 `gone`
  - 결과와 참여 현황: 표 수 합계와 참여 수 일치, 명부에서 뺀 투표자의 참여와 표는 유지, 이름순 정렬, 목록의 투표 완료 표시
  - 삭제: 투표를 삭제하면 선택지, 결과, 참여 기록이 모두 사라짐
  - 비밀 투표: 위에서 말한 스키마 수준 확인 한 개
- **선례**: 구현 직후 실제 Neon DB에 대고 위 동작 대부분을 확인한 일회성 검증 스크립트가 있었다. 저장소에는 남아 있지 않다. 그 시나리오를 Vitest 테스트로 옮겨 정식화한다.

## Out of Scope

- 투표 마감: 수동 마감이나 마감 시각. 나중에 추가한다.
- 복수 선택(Choice Mode). 나중에 추가한다.
- 투표마다 참여 대상 지정(예: 임원진만). 나중에 추가한다.
- 투표 수정, 투표 행위 변경·취소. 결정 기록 0001과 0002에 따라 만들지 않는다.
- 운영자 개인 계정과 운영자별 활동 기록.
- 실시간 결과 갱신(자동 새로고침, WebSocket).
- 한국어 외 언어, 데스크톱 전용 레이아웃.
- 세션 모듈, Server Action, 화면의 자동화 테스트와 브라우저 E2E 테스트.

## Further Notes

- **현재 상태**: 위 동작은 대부분 이미 구현되어 있다. 이 스펙에 따라 남은 일은 두 가지다.
  - 입력 검증을 도메인 모듈 안으로 옮겨 테스트 경계를 하나로 만들기
  - Vitest 기반 도메인 테스트 추가
- **운영자의 한계**: 투표 코드는 원문으로 저장되므로 운영자는 마음만 먹으면 누구로든 투표할 수 있다(결정 기록 0001). 운영자를 신뢰한다는 전제이며, 투표자가 하지 않은 참여는 참여 명단에서 드러난다.
- **비밀 투표의 범위**: 앱 화면과 저장된 값으로는 누가 무엇을 골랐는지 짝지을 수 없어야 한다. 하지만 데이터베이스에 직접 접속하는 사람은 Postgres 트랜잭션 정보(`xmin`)로 일부를 짝지을 수 있으며, 이 한계는 받아들였다(결정 기록 0002의 "보장하지 않는 것"). 따라서 비밀 투표 테스트도 저장된 값과 스키마 수준까지만 확인한다.
- **규모**: 50명 이하 조직을 전제로 한다. 코드 공간(31의 8제곱)은 이 규모에서 충돌이나 추측이 사실상 불가능하다. 코드 입력 시도 횟수는 제한하지 않는다.
